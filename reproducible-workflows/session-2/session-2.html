2 The EDA loop & cleaning decisions

2.1 What EDA is for

Exploratory data analysis (EDA) is the back-and-forth loop where you learn what the data can tell you:

  1. Get a quick sense: shapes, types, missingness, ranges.
  2. Look for problems: wrong types, missing values, inconsistent names/labels, outliers.
  3. Ask & plot: small targeted plots to answer questions and surface surprises.
  4. Record decisions: every cleaning choice documented, because a defensible choice is a feature.

EDA is iterative: you circle through 1–3 several times before any formal modelling. The output that survives into a report is the cleaned data plus the story of your decisions.

Your IDE is part of the reproducible loop. In Positron:

  • Inline plots: plots render in the IDE as you iterate.
  • But: the IDE is for exploring; the document is the record. Anything you discover by clicking must end up as code in a .qmd to be reproducible.

Rule: explore by clicking, report by code. The click is fast; the code is what makes it reproducible.

3 Sourcing open data

3.1 Open data, anywhere in the world

A reproducible analysis needs data it can re-fetch by code, and open-data portals everywhere provide exactly that:

  • France: data.gouv.fr, thousands of public datasets, license-aware.
  • Your own country: nearly every government runs an official open-data portal (data.gov… for the US, Canada, UK, Germany, and many more).
  • The rule is the same wherever you look: a dataset you can fetch programmatically is a dataset your analysis can re-produce.

The reproducible move: don’t download a dataset by hand; write code that sources it, so the analysis is re-runnable and the provenance (publisher + URL) is in the document.

3.3 Fetching any portal by URL

Whatever portal you choose, the reproducible core is the same: a URL your code downloads:

  • download.file() is portal-agnostic: it doesn’t care whether the URL points at data.gouv.fr or your home country’s portal.
  • Pair it with a provenance sentence (dataset, publisher, URL, license) so a reader can find and trust the source.
  • Some portals ship an R/Python client ({rdatagouv} here): a convenience, never a requirement.

4 Versioning your data with {pins}

4.1 The (dis)appearing data problem

Last session you met “the (dis)appearing data”: a fetched file can change or vanish the moment it’s off the portal:

  • A portal updates a dataset: your analysis was based on the old version.
  • A raw URL 404s a year later, and your “reproducible” document can’t re-run.
  • Even locally, data/my-data.csv can be overwritten, and git alone doesn’t version the cached copy well if you don’t commit it.

{pins} closes that gap: version your data the way git versions your code, so a re-render gets the same data a reader expects, not whatever is live today.

markdown
## The (dis)appearing data problem {.inv}

Last session you met "the (dis)appearing data": a fetched file can *change* or *vanish* the moment it's off the portal:

::: {.incremental .highlight-last}

4.2 {pins}: pin data to a versioned board

{pins} stores a data object on a board and records who wrote what, when:

# a folder board that KEEPS HISTORY (versioned = TRUE)
bd <- pins::board_folder(path = "pins/", versioned = TRUE)

# fetch open data once, then pin it:
dat <- readr::read_csv("https://…/my-open-dataset.csv")
pins::pin_write(board = bd, x = dat, name = "my-dataset")        # snapshot it, versioned & hashed

# later re-reads get the PINNED copy, reproducibly:
pins::pin_read(board = bd, name = "my-dataset")

pin_write() snapshots the data and records the version + hash; pin_read() returns that exact snapshot. Re-render → same data, every time.

4.3 Where the versioned copy lives

A board is just a folder (or a service), and it’s fully inspectable:

  • pin_list(board): what’s been pinned.
  • pin_versions(board, "my-dataset"): every snapshot, with hashes and dates.
  • pin_read(board, "my-dataset", version = "…"): roll back to an older snapshot.

The pinned pins/ folder is committed alongside your code, so the exact data your analysis used is reproducible forever, independent of portal changes or broken URLs.

4.4 Fetch once, pin, analyse

A reproducible data workflow in three deliberate steps:

  1. Fetch the open data by URL: provenance recorded.
  2. Pin it with pin_write(): versioned & hashed on a local board.
  3. Analyse from the pinned copy (pin_read()): stable no matter what happens upstream.

Pinning keeps you honest: the data you analysed is on record, not just the code. Combined with git (code), renv/uv (environment) and a URL (delivery), it completes the durable portfolio you build in Session 3.

4.5 Beyond data: version your models too

The same “pin what you made” idea extends to the models you fit, not just the data:

  • {vetiver}: pins a model to a board, so the exact trained model is deployed or re-loaded, versioned & reproducible like your data.
  • It pairs with pin_write()/pin_read(): you already know the mechanics; {vetiver} just knows how to save/load a model’s metadata too.

Same habit, new object

5.4 Branches: keep main always-working

8 Writing for an audience

8.1 A report is read, not just rendered

Your EDA will be read by other humans, instructors, classmates, future employers. Write to them:

  1. Structure signals intent: question, data, cleaning, results, findings.
  2. Captions do the explaining: a reader should grasp a figure from its caption before reading your prose.
  3. Say what you found and what you didn’t: honest limits are credibility.
  4. Keep code in service of the story: the code shows how; the prose says why it matters.

The reproducibility narrative: because everything is code and captioned, a stranger re-rendering your .qmd both trusts and reproduces your work. That’s the product.
